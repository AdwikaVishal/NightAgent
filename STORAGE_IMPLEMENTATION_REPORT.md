## 3. Final Voice Storage Path and Metadata Contract

### Storage Path

```
voice_messages/{chatId}/{senderId}/{messageId}.m4a
```

- `chatId` — deterministic: `sorted([uid1, uid2]).join("_")`
- `senderId` — Firebase Auth UID of the uploading user
- `messageId` — UUID generated by `VoiceMessageRepository.sendVoiceMessage()`
- Extension: `.m4a` (preserved from original implementation)

### Storage Metadata (set on upload)

| Key | Type | Value | Trust level |
|-----|------|-------|-------------|
| `chatId` | string | Canonical chat ID | Client-supplied, NOT trusted |
| `senderId` | string | Uploader's Firebase Auth UID | Client-supplied, NOT trusted |
| `participants` | string | Comma-separated list of participant UIDs | Client-supplied, NOT trusted |

### Authorization Model

| Layer | Responsibility | Trusted? |
|-------|---------------|----------|
| Firestore | Controls who can read `audioUrl` from `chats/{chatId}/messages/{msgId}` | ✅ Trusted (server-enforced rules) |
| Storage | Controls who can download the object at the path | ⚠️ Partial (metadata is client-supplied) |
| Download URL | Bearer token — anyone with the URL can download | ❌ NOT an authorization mechanism |

**Security decision:** Client-supplied Storage metadata is NOT trusted as proof of chat membership. The real gate is Firestore — only participants can read the `audioUrl`. However, a leaked download URL is a bearer token and bypasses Firestore authorization. This requires a production decision: either accept bearer-URL risk or implement signed URLs via Cloud Function (Phase 1C).

## 4. Upload/Download Authorization Explanation

### Upload Flow (sender)

1. `VoiceMessageViewModel.sendVoiceMessage()` computes `chatId = chatId(uid, rid)` and `participants = [uid, rid]`
2. Calls `repository.sendVoiceMessage(file, durationMs, uid, rid, chatId, participants, onProgress)`
3. Repository calls `VoiceMessageFirebase.uploadAudio(file, chatId, uid, participants, messageId, onProgress)`
4. `uploadAudio()` uploads to `voice_messages/{chatId}/{uid}/{messageId}.m4a` with Storage metadata (`chatId`, `senderId`, `participants`)
5. Repository saves message doc to `chats/{chatId}/messages/{messageId}` with `audioUrl` = download URL
6. Repository queues FCM push via `fcm_requests`

### Download/Playback Flow (receiver)

1. `VoiceMessageViewModel.messages` Flow listens to `chats/{chatId}/messages` via Firestore
2. Only chat participants can read this collection (Firestore rules)
3. Receiver's device gets `audioUrl` from the message document
4. `VoicePlayer.playOrPause(messageId, audioUrl, scope)` calls `ExoPlayer` with the URL
5. Storage download: the URL contains a download token; Storage rules check `resource.metadata.participants` contains `request.auth.uid`

**Critical gap:** Step 5 relies on client-supplied metadata. If the uploader set `participants` incorrectly, the wrong users could be granted or denied access. The Firestore rule on `chats/{chatId}/messages/{msgId}` read prevents non-participants from ever seeing the `audioUrl`, but once a participant has the URL, they can share it.

## 5. Legacy-Message Migration and Rollback Plan

### Problem

Existing voice messages were uploaded to `voice_messages/{senderId}/{messageId}.m4a` (old path). Corrected Storage rules match `voice_messages/{chatId}/{senderId}/{messageId}` (new path). Old-path objects fall under the catch-all deny rule.

### Migration Options

**Option A: Dual-path read (recommended for transition)**

Add a temporary Storage rules match block for the old path:

```
match /voice_messages/{senderId}/{messageId} {
  allow read: if isAuthenticated() && resource.metadata != null && validVoiceMetadata(resource.metadata);
  allow delete: if false;
  allow create, update: if false;
}
```

This allows existing files to be read while new uploads use the new path. Delete is disabled on old path to prevent orphaned files.

**Option B: One-time migration (cleaner)**

1. Deploy corrected rules with new path only
2. Android app lists all messages from Firestore `chats/{chatId}/messages`
3. For each message with `audioUrl` on old path, re-upload to new path with metadata
4. Update Firestore `audioUrl` to new download URL
5. Delete old-path objects

**Option C: Keep old path in rules (simplest, less secure)**

Keep `voice_messages/{senderId}/{messageId}` match block for backward compatibility. Less secure because path alone doesn't encode chat membership.

**Recommended:** Option A for immediate compatibility, then Option B for cleanup. Do NOT deploy corrected rules to production without a migration plan.

### Rollback Plan

If issues arise after deployment:
1. Revert Android source changes to use old path and no metadata
2. Revert Storage rules to previous version (or remove rules, reverting to test mode)
3. Existing messages on old path remain accessible
4. New messages during rollback window use old path
